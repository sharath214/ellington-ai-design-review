Design Review Module
Understanding & Client Input Checklist
Based on the discussion for Design & Development Intelligence
Purpose: This document captures our understanding of the agreed Design Review scope and lists the information/materials pending from Ellington before detailed solution design and model validation can progress.
1. Our Understanding of the Agreed Scope
The initial implementation will focus only on the Design Review module covering Stages 3–6 of the wider design and development lifecycle.
The priority use case is to reduce the current manual and error-prone review effort for Concept Design, Schematic Design and Detail Design submissions.
Other stages of the broader lifecycle are deferred for now, including Stage 7 (Project Launch Preparation), Stage 8 (Contractor Tender) and Stage 10 (Post-Contract Parking).
The AI will perform a first-pass compliance and consistency review. It will flag issues for human review; it will not independently approve drawings or issue resubmission instructions.
2. Design Review Inputs
Design submission formats: CAD, BIM and PDF.
Typical file size discussed: Approximately 1 MB per drawing.
Primary review objective: Identify non-compliances, inconsistencies and deviations before the development team sends consolidated comments back to consultants.

4. Project Context / Cross-Discipline Memory
The AI must maintain project context across multiple disciplinary uploads rather than treating each submission in isolation.
Architecture, landscape and other discipline packages must be compared with earlier approved or submitted information so that design intent is carried through.
Example discussed: if an external stair exists in the architecture package but is missing from the landscape drawings, the AI should flag the inconsistency.
This project memory is a core requirement for the Design Review solution, not an optional enhancement.
5. Expected Output and Review Workflow
The user uploads a design submission in the supported format.
The AI performs a first-pass review against the relevant DCR, Ellington Design Standards and approved architectural master plan.
The AI also checks the submission against available project context and previous cross-disciplinary information.
Potential non-compliances or inconsistencies are logged as flagged issues.
The development team reviews the flagged issues and decides what should be communicated to the consultant.
No drawing approval, rejection or resubmission action is completed by the AI without human sign-off.
6. Agreed Development Approach
Use a phased and iterative implementation approach rather than attempting the full solution in one release.
Start with UI/UX design and a workflow prototype so the process can be validated before deeper model development.
Use weekly demo and feedback sessions between Zeero and Ellington to refine the workflow, improve model output and reduce irrelevant or noisy findings.
The target is a refined and scalable solution that can handle the project data and review workflow more effectively than generic AI tools with file-size/context limitations or high-noise output.
